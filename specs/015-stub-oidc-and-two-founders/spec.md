## What changes, stated first

**keel-cloud is about to stop having a password, and the referee logs in with one.**
`stack/auth.py` holds `FOUNDER_PASSWORD = "eval-founder-password-1"` and drives the real `/login`
screen with it. Google sign-in deletes that, and the referee cannot own a Google account — so
either the harness gets a shortcut past the login (and stops refereeing the one thing this feature
changes), or it gets an **issuer of its own**.

§3.6 is the whole test story and it is one sentence: *the issuer is configuration*.
`KEEL_OIDC_ISSUER` defaults to `https://accounts.google.com` and a deployment sets nothing; this
stack sets it to a local stub. There is therefore exactly one login path in keel-cloud and the eval
walks all of it — no `@Profile("test")` login, no `/v2/test-only/login`, no bypass header, no
seeded cookie, and no password anywhere (§10.8).

Three things follow, and they are this half.

1. **`stack/stub_oidc/` — a real OIDC issuer, in the standard library.** Discovery, JWKS,
   `/authorize` with an account picker, `/token` with PKCE, and an ID token signed RS256 that
   verifies against the JWKS it publishes. It is deliberately **strict**: a bad `code_verifier`, a
   reused code, a mismatched `redirect_uri` and an unknown client are all refused, because a stub
   that accepts anything proves nothing about the client's half.
2. **`stack/oidc.py` — the fourth service, and the two founders.** `make up` starts it first,
   `make down` stops it, the gates print it, and the identities (founder A *Eval Founder*, founder
   B *Nour Haddad*) live there, once. The four `KEEL_*` variables keel-cloud will be pointed at it
   with are wired **now**, harmlessly: today's keel-cloud reads none of them.
3. **It is provable on its own, and it is proven.** 46 stackless tests, and a live `make up` walk
   on the eval port: the discovery document, the JWKS, `/authorize?identity=founder-a` → `/token`,
   and the ID token verified. Nothing about this half needs keel-cloud to have changed.

## Clarifications

### How is an RS256 token signed and verified with no `cryptography`? — **`openssl` for the key, `pow()` for the arithmetic**

§10.1 offers two ways out: the `cryptography` package *"the harness already has for nothing"*, or
a committed test key. **This harness has neither.** `requirements.txt` is pytest, playwright,
requests and pyyaml, and playwright's own venv brings no `cryptography` either (checked,
2026-09-09, `.venv/lib/python3.13/site-packages`). And `hashlib`/`hmac` cannot do RSA.

So the decision, taken here and stated in `stack/stub_oidc/keys.py`: the **key** is generated by
`openssl genrsa` at `make up`, into `runs/.stack/oidc-key.pem` beside the pid files; the
**arithmetic** is pure Python, because `pow(m, d, n)` is a built-in and PKCS#1 v1.5 over a SHA-256
DigestInfo is nineteen constant bytes and a run of `0xff`. Both PEM dialects `openssl genrsa`
might write (PKCS#8 on 3.x, PKCS#1 on 1.x) are parsed by a forty-line DER reader.

That buys three things a committed key would not: nothing secret-*shaped* is ever committed, the
key is fresh every `make up` and dies with the run, and signing costs no subprocess per token —
one `openssl` call per boot, none per login. `openssl` is a system tool, not a dependency of this
harness; when it is missing the error says so and names the fix.

**The test verifies with the public half alone**: it reads `n` and `e` off the published JWKS,
recovers the PKCS#1 block with `pow(sig, e, n)`, and compares it against the digest it should be.
It never touches `d`, so it is a verification and not a re-run of the signing code.

### Is `/jwks` or `/jwks.json` the path? — **both; `/jwks` is what discovery names**

§10.1 names `/jwks` and the founder's brief said `/jwks.json`. keel-cloud will never guess either:
it reads `jwks_uri` out of the discovery document, which names `/jwks`. `/jwks.json` is an alias
serving the identical bytes, so a person curling by hand finds it under either spelling. One
assertion pins that they are the same document.

### `?identity=` or `?login_hint=`? — **both, and neither is a bypass**

§10.2 uses `login_hint=<sub>` — the parameter a real client would send. The brief asked for
`?identity=<id>`, a handle a harness can read (`founder-a`). Both are accepted and both resolve
through the same list; an identity also answers to its own email. Whichever is used, it is *the
same code path with the click supplied*: `/authorize` still validates the client, the redirect URI,
the scope and the PKCE challenge, still mints a code, and still redirects to `redirect_uri` — there
is no route that hands out a token without one.

### Does the stub validate `redirect_uri` against a registry? — **no; it requires an absolute URL and pins it through the exchange**

Google refuses a redirect URI that was not registered. The stub has no registry and inventing one
would mean this repository knowing keel-cloud's callback path — a second place for it to live. So
`/authorize` requires an absolute `http(s)` URL (a relative or `javascript:` one is a `400` in the
browser, never a redirect), records it, and `/token` refuses any redemption whose `redirect_uri`
is not byte-identical to it. That is the property keel-cloud's half is actually measured against.

### `state` and `nonce`: optional in the RFC, **required here**

A client this stub exists to referee sends both — `state` is G1's CSRF binding and `nonce` is what
binds the ID token to this login. `/authorize` refuses without either, in the browser, with a
sentence. A keel-cloud that stopped sending one would read as the defect it is rather than as a
green run.

### Does `stub_break` land now, when S-011 lands later? — **yes, and it is proven now**

`?stub_break=<iss|aud|exp|sig|nonce|email_verified>` is §10.1's negative-testing lever and it is
stub machinery, not scenario machinery. Landing it with the stub means S-011 (§10.7, after
keel-cloud 032) starts from an issuer that is *known* to be able to lie in exactly six declared
ways — each one asserted here, against the token it actually produces.

## User Scenarios & Testing

### US1 — the stub issues a token keel-cloud could verify (P1)

**Acceptance** (`tests/test_stub_oidc.py`, stackless — a real server on a real socket)

1. `GET /.well-known/openid-configuration` names its own origin for every endpoint, `code`,
   `RS256` and `S256`.
2. `GET /jwks` serves exactly one key: `kty: RSA`, `use: sig`, `alg: RS256`, `kid: stub-1`, a
   2048-bit modulus, base64url and unpadded. `/jwks.json` is the same document.
3. `GET /authorize` → `POST /token` with a PKCE verifier yields an ID token that **verifies RS256
   against that JWKS** and carries `iss`, `aud`, `azp`, `sub`, `email`, `email_verified: true`,
   `name`, `given_name`, `nonce`, `iat`, `exp` — plus `picture` and `hd` only when the identity
   declares them — and an access token nobody reads.
4. The `state` travels to the issuer and back verbatim; the header names the key by `kid`.

### US2 — the stub refuses (P1)

**Acceptance** (same file)

1. An unknown `client_id` and an unusable `redirect_uri` are refused **in the browser**, never at
   the redirect URI.
2. A missing `state` or `nonce`, a non-`code` response type, a scope without `openid`, and a
   `code_challenge_method` that is not `S256` are all refused.
3. `/token` refuses an unknown code, a bad or missing PKCE verifier, an unknown client, a
   mismatched `redirect_uri`, any grant but `authorization_code`, and a **replayed** code — and a
   code is burned by any redemption attempt, successful or not.
4. Every other path is a `404`.

### US3 — the picker, and the two founders (P1)

**Acceptance** (same file)

1. `/authorize` with no identity answers `200 text/html`: `<h1>Choose an account</h1>` and one
   `<button>` per identity labelled with that identity's **name** — which is what
   `get_by_role("button", name="Eval Founder")` will click when the second half lands.
2. The buttons carry the whole authorize request back, so the click is the same code path.
3. A `Cancel` link redirects with `error=access_denied` and the state, and no code.
4. `?identity=founder-b`, `?login_hint=stub-founder-2` and the identity's own email all skip the
   page and sign in as the same person; an unknown one is a `404` naming the configured ids.

### US4 — a fourth service, per profile (P1)

**Acceptance** (same file, plus the live walk in [tasks.md](tasks.md))

1. `make up` brings the stub up **first**, prints it, and `make down` stops it; `quick_gates_pass`
   includes it, so `make eval` can never attach to a stack with no way in.
2. Ports are fixed per profile: eval **18090**, playground **18091**; pid, log and key names are
   profile-suffixed, so an eval teardown can never touch a playground stub.
3. `stack/cloud.py:build_env` carries `KEEL_OIDC_ISSUER`, `KEEL_GOOGLE_CLIENT_ID`,
   `KEEL_GOOGLE_CLIENT_SECRET` and `KEEL_GOOGLE_REDIRECT_URI` — and **no**
   `KEEL_GOOGLE_ALLOWED_DOMAIN`.
4. Live: `curl` the discovery document and the JWKS on 18090, walk `/authorize?identity=founder-a`
   → `/token`, verify the token, `make down`.

## Requirements

- **FR-001** `stack/stub_oidc/` serves discovery, `/jwks` (and `/jwks.json`), `/authorize` and
  `/token`, standard library only, and `404`s everything else.
- **FR-002** The ID token is RS256 over a key generated at `make up` under `runs/.stack/`, carries
  exactly the claims §3.3 checks, and verifies against the published JWKS.
- **FR-003** The stub refuses a bad verifier, a reused code, a mismatched `redirect_uri` and an
  unknown client (§10.1), and has **no** password, bypass header, test-only route or second
  trusted key (§10.8).
- **FR-004** `/authorize` shows a picker with one button per identity, and accepts `identity`/
  `login_hint` to supply the click for a browserless caller.
- **FR-005** `stack/oidc.py` holds the two identities in one place, founder A keeping today's
  `FOUNDER_NAME`/`FOUNDER_EMAIL`, and the fixed, non-secret client id and secret.
- **FR-006** `stack.toml`, `DEFAULT_PORTS`, `DEFAULT_PLAYGROUND_PORTS` and `StackConfig` carry
  `oidc_port`: eval 18090, playground 18091.
- **FR-007** `lifecycle.boot` starts it first, `quick_gates_pass` checks it,
  `teardown_all_processes` stops each profile's own.
- **FR-008** `stack/cloud.py:build_env` passes the four variables, wired ahead of keel-cloud 032
  and harmless until it lands.
- **FR-009** `make unit` grows, and the growth covers the walk, the refusals, the picker, the six
  `stub_break`s, the key parsing and the lifecycle wiring.
- **FR-010** The second half is **untouched** and says so: `stack/auth.py`, `harness/browser.py`,
  `evals/conftest.py` and the scenario set are unchanged, and one test asserts it.

## What this feature deliberately does not do

- **It does not touch the login.** `stack/auth.py` still has its password and
  `harness/browser.py:log_in` still types it, because that is still the login keel-cloud has.
  Both change in the second half, **after keel-cloud 032**, in the order §12 step 7 gives.
- **It does not write S-010 or S-011.** They need a keel-cloud that reads `KEEL_OIDC_ISSUER`.
- **It does not move `stack/cloud.py`'s readiness gate off `/v2/setup`.** That route still exists
  today; moving the gate before it goes would break every boot. It is the *first* task of the
  second half (§10.3), and it is named there.
- **It does not add a dependency.** No `cryptography`, no `PyJWT`, no `authlib` — see the first
  clarification.
