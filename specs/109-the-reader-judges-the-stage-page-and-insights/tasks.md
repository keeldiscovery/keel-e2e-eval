## Where the spec and the code differ (the code's patterns followed)

- **The leg lives in `Backtest.after`**, not after `_await_standings` in `corpus_scenario.py`: `after` is the one seam
  both walks reach once the answers have settled (the scoped walk's `leg_scoped_report`, the whole study's
  `leg_standings`), and it already waits for the THEMES jobs the Insights screen draws -- so the leg runs on every
  back-test, scoped or not, and `corpus_scenario.py` is unchanged.
- **`insights-open` is not a fold.** keel-web draws `[data-testid=insights-open]` only where a host gives the report
  its links (an example's brief drawer, spec 104 FR-5: *on a project page an Insights box is no link*), and it is a link
  to the stage page, not a fold. The Insights screen's fold is `[data-testid=insights-more]` (*and N more*, expanded in
  place): the leg presses each and shoots once more per fold, and counts any `insights-open` it sees (`opens`) without
  following it.
- **The reader reads the Insights screen once**, with every fold open (its last shot's words); the fold shots are the
  bundle's evidence, nested under it (`folds`), never screens of their own.
- **A §B screen carries no R keys** (`AFTER_SCORE_KEYS`) rather than every key with nulls: a flow screen's score is
  byte for byte version 2's shape, so the fixtures moved by their version alone.
- **The file names** are the spec's: `founder-after-NN-stage.png` on every stage (NN tells an ALL study's three apart;
  the record names the stage), `founder-after-NN-dimension-<key>.png` with the key whole (`problem.prevalence`).

## Test ids keel-web owes (a web follow-up; the leg uses the most stable selectors available)

The stage page draws no `data-testid` at all; the leg reads it by the classes the golden journeys already read it by
(`vectors_screens.Answers.vector_page`):

1. the stage page's root -- `.corridor.answers` today (`DimensionStagePage`): e.g. `data-testid="stage-page"` with
   `data-stage`;
2. its verdict line -- `p.answers__headline`: e.g. `stage-verdict`;
3. a dimension card -- `.dimrow[id=<key>]`: e.g. `stage-dimension` with `data-dim`, and `data-opens` (a LEFT_OUT card
   has no button);
4. the card's head -- `button.dimrow__head`: e.g. `stage-dimension-open`;
5. the opened card's chart -- `.dimrow__drawing` (an `AnswerChart` `.achart[data-chart]`, a `Strip`, or `ul.dimbars`):
   e.g. `dimension-chart` with `data-chart` on every one of the three;
6. the card's verdict line -- `span.status` and its `.sub` (the count): e.g. `dimension-verdict`.

The Insights screen's (`report-insights`, `section.rp-ibox[data-dim]`, `insights-more`, `insights-not-asked`) are
stable already; `insights-open` exists only in an example's drawer (above).

1. **The previous cycle's per-study delta compared across versions**: `cycle.compose` set `previous.studies` from the
   records' score_pct whatever their rubric version; with cycle 4 at 3 after cycle 3 at 2 it would have printed v3 -
   v2 deltas. It names the version and compares nothing now (T003).
2. **The adviser's whys of a §B row**: `failing_screens` built the why key as `why` + the criterion's number, which
   reads `why1` for `b1`; it reads `rubric.WHY_OF` now (T007).
3. **The `read` mark kind goes dark until cycle 4**: every committed score file is version 2, so `read_rows` says
   *not measured* for every entry at version 3 (reported, never gating; no mark moved).
4. **The committed `TABLE.md`** stays cycle 3's, at version 2: it is rebuilt only with a score file, so `make
   read-table` now would draw an empty version-3 table with every file set aside -- cycle 4's first read rebuilds it.
